# SokoHai Inventory Architecture

**Status:** Existing-system audit and safe target architecture; no inventory implementation changed in this phase.
**Date:** 2026-09-26

## 1. Current findings

The current project has inventory-like behavior in several places:

- `products.stock` and `availabilityStatus` are used by product creation, showcase, and seller management.
- `js/app/15-pos-sales.js` updates product stock directly and creates offline/POS products in the existing `products` collection.
- `js/app/30-seller-products.js` reads product stock and currently updates `products.stock` from the client.
- `html/21-scripts.html` contains `offlineStockModal`.
- `firestore.rules` contains product stock validation and separate collections such as `stock_transfers`, `purchase_orders`, `shop_ledger`, and `shift_logs`.
- Checkout/order/SokoPay/delivery systems already exist and must not be replaced.

The audit did not find one clearly consolidated, server-authoritative inventory ledger with all requested event types. Therefore the first safe action is mapping and contract testing, not silently converting `products.stock` into a new inventory system.

## 2. Required ownership boundary

```text
PRODUCT
  identity, title, media, taxonomy, commercial defaults

VARIANT
  option combination and variant identity

INVENTORY
  quantities and reservations for a product/variant at a store

ORDER
  committed purchase and payment/delivery state
```

Product and variant are not inventory. Discover is not inventory. The checkout client must not be the authority for available quantity.

## 3. Target inventory model

A future implementation may use an inventory document keyed by Store + Product + Variant, subject to existing collection/rules review:

```text
inventoryId
storeId
businessId
productId
variantId          // nullable for non-variant products
currentQuantity
reservedQuantity
incomingQuantity
unavailableQuantity
damagedQuantity
soldQuantity
lowStockThreshold
status
updatedAt
```

Availability should be derived, not independently typed by the UI:

```text
availableQuantity = currentQuantity - reservedQuantity - unavailableQuantity
```

Negative quantities must be rejected server-side.

## 4. Event model

Inventory changes should be traceable using an append-only event/audit model:

```text
STOCK_RECEIVED
STOCK_ADJUSTED
STOCK_RESERVED
STOCK_RELEASED
STOCK_SOLD
STOCK_RETURNED
STOCK_DAMAGED
STOCK_TRANSFERRED
```

Each event should contain:

```text
eventId
productId
variantId
storeId
actorUid
quantity
reason
referenceType
referenceId
createdAt
```

Order/payment-related events must be generated by trusted server code or transactions. A frontend button may request an operation, but may not assert that it succeeded.

## 5. Migration from current fields

Do not delete `products.stock` in the first implementation step.

Recommended sequence:

1. Inventory all current stock writers and readers.
2. Define whether legacy `products.stock` represents total current quantity, available quantity, or POS quantity in each existing flow.
3. Add tests for old product documents and non-variant products.
4. Introduce an adapter that reads canonical inventory when present and safely falls back to legacy stock during migration.
5. Migrate selected records with auditability.
6. Move writes behind server-authoritative operations.
7. Remove or freeze direct client stock writes only after all callers are migrated.

## 6. Existing-risk findings

- `js/app/30-seller-products.js` currently performs a direct client `updateDoc` of `products.stock`.
- `js/app/15-pos-sales.js` uses a client increment for received stock and direct product creation for offline inventory.
- Product rules validate some stock fields, but existing rules must be reviewed before claiming complete concurrency safety.
- The requested reserved/incoming/damaged/sold dimensions are not demonstrated as one canonical record in the current implementation.

These are implementation gaps to address in a dedicated, tested phase. They were not changed in this audit.

## 7. Required future operations

Every operation must define:

- authenticated actor and store ownership;
- product/variant identity;
- quantity and reason validation;
- idempotency/reference ID where relevant;
- transaction or atomic update behavior;
- event/audit record;
- response state (`PENDING`, `SUCCESS`, `FAILED`) for network resilience.

Required concurrency tests:

- two simultaneous reservations;
- reservation release after cancellation;
- sale against reserved stock;
- return after sale;
- damaged quantity adjustment;
- duplicate request retry;
- variant-specific stock isolation;
- offline POS sync conflict.

## 8. Dashboard projection

Seller UI may display:

```text
Current
Reserved
Available
Incoming
Damaged
Sold
Low stock
History
```

These values must be read from the same inventory authority used by order validation. No separate dashboard stock cache may become authoritative.

## 9. Not implemented in this audit phase

No new inventory collection, Cloud Function, rule, migration, or product stock rewrite was made. Existing Product, Order, POS, SokoPay, and Delivery behavior is preserved.
