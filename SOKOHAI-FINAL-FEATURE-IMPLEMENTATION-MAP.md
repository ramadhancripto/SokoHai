## 1. Production path / active files

`index.html` is the active root entry point. It loads canonical `js/` modules and `functions/` is the server source. `assets/js/`, `_old_fonts_project/`, `_originals/`, and `fonts/` were treated as copies, generated variants, or historical checkpoints, not independent systems.

Relevant active loading order:

- `js/app/00-bootstrap.js` — Firebase/Auth/Firestore/Functions and shared state.
- `js/app/01-market.js` through commerce modules — marketplace and sale modes.
- `js/app/07-product.js` — product detail, media, auction/group-buy/price-drop UI and actions.
- `js/06-announcement.js` — canonical announcement/ad rendering, video/audio poster-first behavior.
- `js/app/95-creative-studio.js` — existing ad/creative editor and audio/video preview.
- `js/app/96-ad-delivery-controller.js` — one shared client ad delivery controller.
- `functions/ads-delivery-core.js` + `functions/ads-delivery.js` — central server ad eligibility, leases, tracking, frequency, and delivery.
- `shared/ads-design-rules.js` — shared creative validation/projection rules.
- `functions/index.js` — existing authoritative payment, escrow, delivery/custody, notifications, comments, and ad exports.

## 2. Existing feature audit

### 2.1 Video

Current implementation:

- Product media renders `<video controls muted playsinline preload="metadata">` in `js/app/07-product.js`.
- Announcement/ad video is rendered by `js/06-announcement.js` with poster support, trim metadata, optional controls, muted/playsinline behavior, and a delegated click-to-play cue.
- Creative Studio has video preview and user-gesture playback in `js/app/95-creative-studio.js`.
- Chat/comments render video with controls and metadata preload.
- `js/app/96-ad-delivery-controller.js` owns ad viewport/lazy/viewability lifecycle, but it is not a general media coordinator.
- `js/app/06-navigation.js` pauses/removes video sources during navigation in the relevant path.

Current gaps/root risks:

- No single global video coordinator pauses every non-ad/product video when another video starts.
- Product videos are primarily user-controlled; there is no verified general visibility-based play/pause policy for product cards.
- Announcement playback has trim/click handling, but the audit needs to verify cleanup when the host is removed and behavior when the document becomes hidden.
- Network/error/poster fallback behavior is distributed across renderers rather than one media policy.

Reusable code:

- `js/06-announcement.js` video cue/trim logic.
- `js/app/96-ad-delivery-controller.js` IntersectionObserver lifecycle pattern.
- Existing navigation pause logic in `js/app/06-navigation.js`.

Minimal proposed fix:

- Extend the existing media lifecycle helpers, preferably in `js/06-announcement.js` or a small shared helper only if the current module boundaries require it.
- Do not touch Posts unless a shared helper proves that Posts are affected.
- Add a coordinator for videos generated by SokoHai surfaces: pause out-of-view media, pause on document hidden, preserve user-controlled full controls, and show poster/failure state.
- Reuse current ad/product markup and avoid a new video engine.

Compatibility risk: autoplay policy differs across mobile browsers; default should remain muted/poster-first and user gesture should unlock controls/audio.

### 2.2 Audio

Current implementation:

- Creative Studio uses one module-level `audioElement` in `js/app/95-creative-studio.js` for preview, mute, volume, and replacement.
- Chat voice capture uses the existing `MediaRecorder` path in `js/app/34-chat-core.js` and `js/app/07-product.js`.
- Announcement audio renders an `<audio controls>` element in `js/06-announcement.js`.
- Bootstrap contains a local Web Audio fallback for notification-like sounds.

Current gaps/root risks:

- Creative Studio's single audio element is local to that module, not a global one-active-session coordinator.
- Announcement audio elements and Creative Studio preview can coexist and compete.
- MediaRecorder cleanup is present in chat paths but needs explicit stream-track verification on every stop/error/navigation path.

Minimal proposed fix:

- Reuse the existing `audioElement` concept and expose a narrow shared playback coordinator only for preview/announcement playback.
- Ensure starting one managed audio session pauses the previous managed session.
- Do not merge voice-recording transport with playback; keep Chat voice notes separate.

### 2.3 Posts

Posts are not a target of this phase. The audit found media rendering in bootstrap/comments/chat, but no evidence requiring a Posts rewrite. Posts must remain untouched unless the shared media fix demonstrates a direct regression.

## 3. Existing Ads architecture

SokoHai already has a central Ads system rather than separate inbox/discover/dashboard engines.

### Current model

- Campaign content is primarily stored under `announcements` with shared creative fields.
- `js/app/95-creative-studio.js` and admin form code in `js/app/16-pos-admin-jobs.js` create/edit creative content, schedule, draft, publish, preview, and media.
- `shared/ads-design-rules.js` is the shared validation/projection source for Basic/Advanced creative flows and server packaging.
- `functions/ads-delivery-core.js` defines central placements including `home`, `discover`, `search`, `product_detail`, `service_detail`, `chat`, `groups`, `live`, `auction`, `group_buy`, `price_drop`, and `dashboard`.
- `functions/ads-delivery.js` implements server-side candidate selection, lifecycle, targeting, frequency/cooldown/fatigue, leases, viewability, tracking, and no-ad reasons.
- `js/app/96-ad-delivery-controller.js` handles DOM slots, lazy requests, leases, viewport/viewability events, rotation, fail-open behavior, local preview behavior, and protected contexts.
- `functions/index.js` exports `adsRequestDelivery`, `adsTrackDeliveryEvent`, `adsUpdateCampaignDelivery`, and the scheduled `adsDeliverySweep`.

### What is already covered

- Central eligibility vs placement separation.
- Frequency/session/hour/day controls and cooldowns.
- Server leases and event tracking.
- Protected payment/admin/security contexts.
- Home/product detail/chat-inbox slots already exist in `index.html`.
- Creative preview/rendering and media duration limits already exist.
- Ads tests are extensive: governance, delivery engine, local delivery regression, creative system, non-canvas designer, and billing-coming-soon contracts.

### Current product gap

Advertiser billing is explicitly marked Coming Soon. The existing creative flow is closer to an admin/announcement publisher than the requested advertiser wizard with objective, object selection, audience, surfaces, schedule, budget, preview, and publish. The billing boundary must not be bypassed.

### Minimal proposed Ads work

- Extend existing `announcements`/creative model with structured campaign metadata rather than create a second campaign collection or delivery engine.
- Reuse the existing `targeting`, `placements`, lifecycle, policy, lease, and tracking fields already consumed by `ads-delivery-core.js`.
- Add an advertiser wizard only where the current admin/creative form can be extended safely.
- Selection of an existing product/service/business/live object should store a reference (`targetType`, `targetId`) and project public content at render time; do not duplicate product data.
- Keep budget/payment disabled until a trusted billing operation exists. A campaign cannot be treated as paid/financially active from client state.

## 4. Existing commerce modes versus Live Commerce

### Existing product mode implementation

`js/app/01-market.js`, `js/app/05-forms.js`, `js/app/07-product.js`, `js/app/02-checkout.js`, and `js/17-pesapal-return.js` already support product sale modes:

- `auction`
- `price_drop`
- `group_buy`
- `wholesale`

The product remains the source of truth in `products/{productId}` with `saleMode` and `modeData`. The detail UI computes mode state and displays current bid, price-drop price, group-buy progress, timers, and CTAs.

Existing actions include:

- `skhAuctionPlaceBid`
- `skhGroupBuyJoin`
- `skhPriceDropCheckout`
- winner checkout through existing order/payment flow
- snapshot listeners on the current product
- notifications through the existing notification helper

### Critical finding

There is no active shared `live_sessions/{sessionId}` engine, no common live shell, and no server-authoritative Live Product/Live Group Buy/Live Price Drop/Live Auction session model in the inspected repository. Existing mode logic is product-centric and some mode actions are browser-side Firestore writes.

Therefore the requested Live Commerce work cannot safely be implemented by only adding UI labels. It requires a new shared session layer or a carefully scoped extension of an existing realtime/session service. This is a blocking architecture decision for the next phase and must not be hidden inside `js/app/07-product.js`.

### Reusable pieces

- Existing product mode computation and visual panels.
- Existing product snapshot listener.
- Existing notifications.
- Existing Chat infrastructure for private seller contact.
- Existing Functions for orders, PesaPal, escrow, delivery, and server authority.
- Existing Ads delivery placement key `live` and mode-specific placement keys.

### Required future design, before implementation

A single `live_sessions` model would be needed with:

- host/product/session type references
- lifecycle state
- participants/presence strategy
- live event stream
- comments/reactions separate from private Chat
- server Functions for JOIN/BID/price change/start/end/threshold/payment transitions
- concurrency-safe transactions

That is a substantial next phase. It must not duplicate `products`, `orders`, `payments`, `escrow`, or private Chat.

## 5. Automation map

### Existing, reusable automation

- Product snapshot → mode UI refresh.
- Product mode lifecycle → client notifications and status flags.
- Ads campaign → server eligibility → lease → viewability/tracking → rotation.
- Announcement video click → play/pause and trim handling.
- Creative Studio save/publish → shared validation/projection → existing announcement pipeline.
- Existing scheduled ad delivery and SokoPay/delivery schedules remain separate.

### Missing/unsafe automation

- Server-authoritative live session state machine.
- Server-authoritative concurrent group-buy joins.
- Server-authoritative live auction winner/bid stream in a session context.
- Central one-active-audio policy across all surfaces.
- General product/live video visibility coordinator.
- Structured advertiser objective/object reference wizard integrated with billing constraints.

## 8. Compatibility risks

- Browser autoplay and audio policies vary, especially on mobile.
- Changing product mode writes from client to server would affect existing checkout paths and must be done through existing order/payment Functions.
- Introducing `live_sessions` without linking to `products`, `orders`, `notifications`, and Ads would create duplicate truth.
- Adding advertiser budget/payment before trusted billing exists would create financial risk.
- Adding live comments to private `conversations` would corrupt Chat semantics; live interaction needs a separate session event stream.
- Existing Posts must not be modified merely to share media code.

## 9. Audit conclusion

The repository already contains a substantial centralized Ads delivery engine and a product-mode implementation for auction, group-buy, and price-drop. It does not yet contain the requested shared Live Commerce session engine. The correct next implementation step is not a broad feature build; it is a narrowly scoped media automation pass followed by a reviewed live-session architecture and concurrency/security design.
