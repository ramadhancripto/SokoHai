### Product data path currently observed

```text
Add Product UI
  -> window.submitSeller
  -> skh.saveData('products', data)
  -> skh.buildProductWrite(data)
  -> skh.validateProduct(canonicalData)
  -> Firestore products collection

Edit Product UI
  -> window.openEditModal
  -> Firestore products/{productId} read
  -> window.submitEditForm
  -> skh.buildProductWrite(merged data)
  -> updateDoc(products/{productId}, patch)

Buyer Product Details
  -> openProduct(productId, collection)
  -> products/{productId} listener
  -> skhRenderShowcase(product, collection)
  -> existing cart/order/checkout handlers

POS
  -> products collection and existing product identity
  -> protected POS identity fields and server authorities
```

## B. File → function → data → authority → path → UI → consumers

### Add Product

- UI: `#sellerForm` in `html/09-admin-sell.html`.
- Main handler: `window.submitSeller` in `js/app/08-app-state.js`.
- Additional form behavior: `generateSellerFilters` in `js/app/05-forms.js`; visibility switching in `js/app/14-map-onboarding.js`.
- Data currently collected: title, category, subcategory, filters, description, images, location, price, buy price, stock, base unit, barcode, bulk packaging, expiry/batch/IMEI fields, sale mode, variants text, product type, condition, publication and availability status.
- Save authority: existing `skh.saveData('products', data)`; this is the current product creation authority.
- Firestore path: `products` collection; IDs are generated by existing `addDoc` path.
- Consumers: dashboard/product feed, seller product list, product details, marketplace cards, search metadata, POS product collection.
- Finding: the form collects many fields, but options/selectors/variant combinations/variant images/features are not first-class UI sections.

### Edit Product

- UI: `#editModal` in `html/13-form-edit.html`.
- Main handlers: `openEditModal` and `submitEditForm` in `js/app/12-sys-modes.js`.
- Existing edit fields: title, price, location, description, publication, availability, product type, condition, variants text, concrete variant combinations JSON, sale-mode fields.
- Save authority: existing `updateDoc` path after reading the fresh document and passing merged data through `buildProductWrite`.
- Firestore path: `products/{productId}`.
- Finding: Edit supports raw JSON concrete variant combinations but does not provide a visual option/variant manager equivalent to the requested workflow. Image relationship editing is not present in the inspected edit form.

### Product identity and normalization

- Core: `js/app/39-product-core.js`.
- Existing compatibility behavior: legacy category/subcategory/title fields are preserved; additive `taxonomy` metadata can be normalized; `schemaVersion` is set to 2 by `buildProductWrite`.
- Existing variant normalization: simple `name + options` values and strict concrete combinations with `variantId`, `sku`, `unitId`, `price`, `stock`, `inventoryKey`, and status.
- Finding: concrete variant validation is materially stronger than the seller UI that produces it. The requested visual generation/review/enable workflow is missing.

### Product Details / Buyer Selection

- Shell: `html/05-modals-market.html`.
- Open/listener: `js/app/07-product.js`.
- Renderer: `js/app/39-product-showcase.js`.
- Existing behavior: media gallery, product identity, price, details, delivery/payment sections, dynamic variant area, cart/checkout actions, seller information, related products.
- Existing variant behavior: renderer supports data-driven variant groups and selected values; actual behavior is based on available product data and existing variant representations.
- Finding: the shell has a dynamic `pmVariantSelectionArea`, but no verified general-purpose option selector registry with color/image/swatch/dropdown/custom selector types.

### Images

- Shared uploader: `js/11-uploads.js` and shared `skhInitPhotoPicker`/`skhUploadPicked` path.
- Add Product behavior: general product images, primary image plus additional images, maximum observed in form is six.
- Buyer behavior: `skhNormalizeImages` and product gallery in `js/app/07-product.js`.
- Finding: general product gallery exists. First-class option-image, variant-image inheritance/reuse, and observable-feature image relationships were not found in the audited Add/Edit UI path.

### Search and filters

- Product foundation: `filterProducts`, `scoreProduct`, `buildSearchMetadata` in `js/app/39-product-core.js`.
- Seller form: legacy category/subcategory filters from `skh.advancedCategories` via `generateSellerFilters`.
- Buyer/search: `js/20-search-chat.js`, `js/21-home-filters.js`, and feed/product foundation consumers.
- Finding: product data can contribute to search metadata and filters, but the requested automatic mapping of arbitrary custom attributes into buyer filters is not yet demonstrated by the audited implementation.

## C. Existing / incomplete / risky classification

### Existing + working

- Existing product ID and Firestore `products` path.
- Existing Add Product and Edit Product entry points.
- Existing product details modal and marketplace product opening.
- Existing general product image upload and gallery.
- Existing category/subcategory selection in the seller form.
- Existing seller filter generation from legacy category configuration.
- Existing product normalization and backward-compatible legacy field handling.
- Existing concrete variant identity validation.
- Existing POS product collection and protected POS identity fields.
- Existing seller product list and edit/view actions.

### Existing + incomplete or needs refinement

- Category-aware suggestions are present in legacy form configuration but are not verified as a complete canonical category-by-category upload experience.
- Product form is a large single form rather than a progressive Basic → Classification → Details → Options → Variants → Pricing → Additional workflow.
- Filter fields are rendered as text inputs and are labelled required in generated UI, even though the requested behavior is guidance rather than mandatory completion.
- Variants are currently text-based for ordinary entry and JSON-based for concrete combinations in Edit.
- Product Details has a dynamic variant area, but generalized selector types and availability-aware combination behavior require category-by-category verification.
- Product image handling exists, but option/variant/feature image relationships are not first-class in the reviewed upload/edit path.
- Edit Product does not expose the same structured capabilities as the requested refined Add Product flow.

### Missing from the audited implementation

- First-class custom attribute creator with name/value/type/source/display/search metadata.
- First-class filter mapping UI from populated product data.
- First-class option builder with selector type and add-value controls.
- Image selector support for option values.
- Visual variant combination generator with Generate → Review → Enable controls.
- Manual variant add flow with complete identity/pricing/stock controls.
- Variant image inheritance/reuse relationships.
- Observable feature model and feature-image relationships.
- Buyer-facing rendering of populated technical attributes/features as structured sections with empty-data suppression verified across categories.
- Product-name suggestion flow with seller-controlled Use/Edit/Remove/Add custom/Skip behavior, as a complete product-upload feature.

### Risky to change

- `skh.saveData('products', data)` and `buildProductWrite` because all product writes pass through them.
- `submitEditForm` because it updates existing product documents and protects transaction-bearing sale modes.
- `shared/pos-product-identity-core.js` because POS identity is protected.
- `variantCombinations`, `inventoryKey`, `productId`, `variantId`, `sku`, `unitId`, and stock paths.
- Existing `products` document fields used by marketplace, seller dashboard, POS, orders, receipts, and inventory.
- Canonical taxonomy wiring because the canonical files currently state they are not wired into Product/POS/Search/Firestore behavior.

## H. Potential problems / follow-up

1. Two configuration worlds exist: live seller UI uses legacy `skh.advancedCategories`; canonical taxonomy registries are separate and explicitly not wired into product upload behavior.
2. The Add Product form and Edit Product form do not expose the same product structure.
3. `filters` are currently used as seller-entered fields, but the requested model distinguishes product data from buyer filter mapping.
4. Ordinary variants are entered as text; concrete variants are entered as JSON in Edit. This is not yet a seller-friendly selectable variant workflow.
5. General product images exist, but option/variant/feature image relationships are not established as a stable existing contract.
6. Category coverage cannot be claimed merely from the existence of a large category tree or canonical registries.
7. `CAT-19`, `CAT-16`, `CAT-42`, `CAT-43`, overlays, services, and fallback boundaries require context-safe handling and must not be flattened into a generic product form.
8. Product form validation currently requires category for online products and description/location/price/image conditions in the existing path. Any relaxation must distinguish genuinely required identity/commerce fields from optional guidance fields.
9. Any change to variant identity must preserve POS fields and inventory identity: `productId`, `variantId`, `sku`, `unitId`, and `inventoryKey`.
